# DreamGuard — Product Requirements Document (PRD)

**Product:** DreamGuard  
**Track:** Dream Labs — Build a Tool for Dream-1 Users  
**Product type:** Safety middleware for AI-driven robotics  
**Status:** MVP / Hackathon development  
**Platform:** Dream-1 Simulator / Playground  
**Primary language:** Python 3.12

---

## 1. Executive Summary

DreamGuard is an intelligent safety supervisor middleware layer designed to make AI-driven robot actions safer and more predictable.

It sits between Dream-1's action generation and the robot controller. Before an action reaches the simulator or controller, DreamGuard intercepts and validates it against configurable safety rules.

If the action is safe, DreamGuard allows it to proceed. If it violates a safety constraint, DreamGuard blocks it or, where explicitly configured, modifies it into a safer action.

DreamGuard also records safety decisions so developers can inspect why an action was approved, modified, or rejected.

**Core idea:**

> Let Dream-1 decide what the robot should do, but let DreamGuard verify whether it is safe to do it.

The initial version will focus on simulated robot actions and demonstrate that unsafe commands can be detected before execution.

---

## 2. Problem Statement

AI-powered robot policies can generate actions that are technically valid but unsafe.

Examples include:

- Moving a robot joint beyond its permitted range.
- Making an excessively large movement between consecutive actions.
- Moving an end effector outside a defined workspace.
- Bringing two robot end effectors too close together.
- Producing invalid numerical values such as NaN or infinity.
- Sending an action that cannot be validated because required safety information is missing.

A robot controller may accept an action without knowing whether it is appropriate for the environment.

DreamGuard addresses this problem by introducing a dedicated safety validation layer before execution.

### The problem we solve

There is a gap between an AI policy generating an action and a robot safely executing that action.

DreamGuard fills that gap.

---

## 3. Product Vision

Build a reusable safety supervision layer that can work alongside Dream-1 and eventually other AI-driven robotic systems.

DreamGuard should make it easier for developers to:

1. Inspect actions generated by an AI policy.
2. Define safety rules without rewriting the policy.
3. Prevent unsafe actions from reaching the controller.
4. Understand why an action was blocked.
5. Test safety behavior in simulation.
6. Review safety decisions through logs and replay tools.

### Product principles

- **Safety first:** Invalid or unverified actions should not reach the controller.
- **Transparent:** Every safety decision should have an understandable reason.
- **Modular:** Safety rules should be independently configurable.
- **Developer-friendly:** Integration should require minimal changes to an existing Dream-1 workflow.
- **Fail closed:** If a required safety check cannot be completed, the action should be rejected.

## 5. Proposed Solution

DreamGuard operates as middleware between Dream-1 and the robot execution environment.

### System workflow

1. A user provides an instruction to Dream-1.
2. Dream-1 generates a robot action.
3. DreamGuard intercepts the generated action.
4. DreamGuard validates the action against its safety rules.
5. DreamGuard makes a decision:
   - Approve: allow the action through.
   - Modify: adjust the action if a safe, explicitly configured correction is available.
   - Block: prevent execution.
6. The decision and its reasons are recorded.
7. Only approved actions are passed to the robot controller.

### Architecture

```text
             User Instruction
                    |
                    v
                Dream-1
                    |
                    v
           Generated Robot Action
                    |
                    v
          +----------------------+
          |      DreamGuard      |
          |                      |
          |  1. Input Validation |
          |  2. Joint Limits     |
          |  3. Movement Limits  |
          |  4. Workspace Checks |
          |  5. Collision Checks|
          |  6. Risk Assessment  |
          +----------------------+
                    |
             Safety Decision
                    |
          +---------+---------+
          |         |         |
          v         v         v
        APPROVE   MODIFY     BLOCK
          |         |         |
          v         v         v
        Robot     Robot     No action
      Controller Controller executed
          |
          v
       Simulator
```

## 6. Functional Requirements

### FR-01: Action interception

DreamGuard must receive actions generated by Dream-1 before those actions are passed to the robot controller.

**Acceptance criteria:**
- DreamGuard can inspect an action before execution.
- The original action can be evaluated without executing it first.
- The integration provides a clear approved/rejected result.

### FR-02: Input validation

DreamGuard must check whether the action contains valid and usable values.

Checks include:
- Required action fields are present.
- Joint values are numeric.
- Values are finite.
- Expected action dimensions are correct.
- Gripper values are within the permitted range.

**Acceptance criteria:**
- Missing fields are rejected.
- NaN and infinity values are rejected.
- Incorrect action dimensions are rejected.

### FR-03: Joint-limit validation

DreamGuard must check that commanded joint positions fall within configured joint limits.

**Acceptance criteria:**
- Each joint is checked against its configured minimum and maximum.
- An out-of-range joint causes the action to be rejected.
- Joint limits are configurable rather than assumed to be universal.

### FR-04: Movement-limit validation

DreamGuard must compare proposed joint positions against the current robot joint positions.

This prevents excessively large movements between consecutive actions.

**Acceptance criteria:**
- The system calculates the difference between current and proposed joint positions.
- The difference is checked against a configurable maximum step.
- Excessive movement is rejected or handled by an explicitly configured correction policy.

### FR-05: Workspace validation

DreamGuard should support forward-kinematics-based workspace checks.

The system should verify that the robot end effector remains within a configured safe region.

**Acceptance criteria:**
- Workspace bounds can be configured.
- A forward-kinematics function can be supplied.
- Positions outside the workspace are rejected.
- If workspace validation is mandatory but unavailable, the action is rejected.

### FR-06: Collision-risk validation

The MVP should support a basic proximity check between robot end effectors when suitable position data is available.

**Acceptance criteria:**
- A minimum separation distance can be configured.
- Actions violating the configured separation are rejected.

**Important limitation:** An end-effector distance check is not equivalent to full robot collision detection. It does not validate every robot link or environmental obstacle.

### FR-07: Risk assessment

DreamGuard should produce a risk assessment for each action.

The assessment should include:
- Overall risk score.
- Safety findings.
- Validation decision.
- Explanation of any violations.

The risk score is intended as a developer-facing heuristic, not a certified probability of injury or collision.

### FR-08: Action decision

DreamGuard must support three decision types:

| Decision | Meaning |
|---|---|
| APPROVE | Action passed all required checks. |
| MODIFY | A safe, configured correction was applied and revalidated. |
| BLOCK | Action must not be executed. |

The MVP should prioritize APPROVE and BLOCK. Modification should only be enabled for clearly defined corrections that are revalidated before execution.

### FR-09: Safety logging

DreamGuard should record:
- Action identifier, where available.
- Timestamp.
- Safety decision.
- Risk score.
- Failed checks.
- Relevant validation details.

The initial version can log to the console. SQLite can be introduced as a later improvement.

### FR-10: Safety replay

A later version should allow developers to replay recorded actions and inspect why each action was approved or rejected.

## 7. MVP Scope

The hackathon MVP should demonstrate a working safety supervisor rather than attempting to implement every possible robotics safety feature.

### Included in MVP

1. Python safety middleware.
2. Dream-1 action interception.
3. Action structure and numeric validation.
4. Joint-limit checking.
5. Maximum joint-step checking.
6. Optional workspace validation through a forward-kinematics callback.
7. Optional end-effector separation check.
8. Safety decision and risk reporting.
9. Demonstration of safe and unsafe actions.
10. Automated tests.

### MVP demonstration scenarios

| Scenario | Expected result |
|---|---|
| Normal movement within configured limits | APPROVE |
| Joint target outside configured limits | BLOCK |
| Excessively large joint movement | BLOCK |
| Missing required action field | BLOCK |
| NaN or infinite value | BLOCK |
| End effector outside configured workspace | BLOCK when workspace validation is enabled |
| End effectors closer than permitted | BLOCK when proximity validation is enabled |

### Out of scope for MVP

- Certified industrial robot safety.
- Full robot-link collision detection.
- Physical emergency-stop implementation.
- Autonomous obstacle avoidance.
- Production-grade safety certification.
- Comprehensive graphical dashboard.
- Multi-robot coordination.
- Automatic recovery from every unsafe action.

## 9. Dream-1 Integration

The planned integration uses the Dream Labs Python SDK.

The starter project assumes the following integration concepts and example interface:

- Import the `dream` package.
- Construct a `dream.DreamClient`.
- Create a policy using the documented policy configuration.
- Supply observations to the policy.
- Retrieve an action.
- Pass that action through DreamGuard before execution.

The starter integration references the action fields:

- `q_r_chunk`
- `q_l_chunk`

The action representation is expected to contain joint targets and a gripper value for each row.

**Integration requirement:** Confirm the exact installed SDK version, action schema, policy configuration, observation format, and simulator execution method against the current Dream Labs documentation and official Playground example. The example integration file intentionally leaves simulator-specific observation and camera mappings for this verification.

DreamGuard must never assume that an action has been validated merely because the SDK returned it successfully.

## 10. Safety Requirements and Limitations

Safety is the defining product requirement.

### Required behavior

- Reject malformed actions.
- Reject invalid numeric values.
- Reject out-of-range joint targets.
- Reject excessive joint movement.
- Reject actions that fail mandatory workspace checks.
- Reject actions when required validation information is missing.
- Ensure blocked actions never reach the controller.
- Log why an action was rejected.

### Fail-closed behavior

If a mandatory safety check cannot be completed, DreamGuard must not approve the action.

For example, if workspace validation is required but no forward-kinematics function is available, the action should be blocked.

### Configuration warning

Default joint bounds in the starter implementation are placeholders. They must be calibrated to the actual robot model and simulator.

### Physical robot warning

DreamGuard is a development and simulation safety layer. It is not a certified safety controller and must not be used as the sole safety mechanism for a physical robot.

Any physical deployment requires independent, appropriately certified safety systems, physical emergency stops, hardware limits, risk assessment, and qualified engineering review.

# 17. Installation and Setup Guide — Windows

This section assumes Windows, Python 3.12, a Dream Labs account, and an API key.

The local safety demo and tests can run without an API key. The key is only needed for the relevant Dream Labs integration checks and API usage.

## Step 1 — Download the starter project

Download the DreamGuard starter ZIP supplied with the project.

Extract it into:

```text
C:\dev
```

For example, if the ZIP is in Downloads, open PowerShell and run:

```powershell
New-Item -ItemType Directory -Force C:\dev
Expand-Archive "$HOME\Downloads\dreamguard_starter.zip" -DestinationPath C:\dev
```

Then navigate into the project:

```powershell
cd C:\dev\dreamguard
```

Confirm that the project files are present:

```powershell
Get-ChildItem
```

You should see `src`, `scripts`, `examples`, `tests`, `pyproject.toml`, and `README.md`.

## Step 2 — Verify Python

Run:

```powershell
py -3.12 --version
```

Expected result:

```text
Python 3.12.x
```

If this command does not work, verify that Python 3.12 is installed and available through the Windows Python launcher.

## Step 3 — Create a virtual environment

From the project directory:

```powershell
py -3.12 -m venv .venv
```

Activate it:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

Your PowerShell prompt should now show `(.venv)`.

A virtual environment keeps project dependencies separate from other Python projects.

## Step 4 — Install project dependencies

Upgrade pip:

```powershell
python -m pip install --upgrade pip
```

Install DreamGuard and its development dependencies:

```powershell
python -m pip install -e ".[dev]"
```

This installs the project in editable mode, along with its declared dependencies and testing tools.

If installation fails, save the complete error output before changing dependency versions.

## Step 5 — Run the local demonstration

Run:

```powershell
python -m dreamguard.demo
```

This exercises the local safety engine using synthetic actions.

The expected behavior is that a valid action is approved and an unsafe action is blocked with a reason.

This step does not require a live Dream-1 connection.

## Step 6 — Run automated tests

Run:

```powershell
python -m pytest -q
```

The starter project contains seven tests covering:

1. Safe action approval.
2. Missing required arm action data.
3. Excessive joint movement.
4. Joint-limit violation.
5. Invalid gripper range.
6. NaN input rejection.
7. Workspace validation behavior.

Expected result:

```text
7 passed
```

The exact test output may differ slightly by pytest version.

Do not proceed to integration debugging until the local tests pass. If they fail, keep the full PowerShell error output for troubleshooting.

## Step 7 — Configure the Dream Labs API key

Once local tests are passing, create your local environment file:

```powershell
Copy-Item .env.example .env
notepad .env
```

Replace the placeholder with your actual Dream Labs API key:

```env
DREAM_API_KEY=your_actual_api_key
```

Save and close Notepad.

**Security requirements:**
- Never share your API key in screenshots or chat.
- Never commit `.env` to GitHub.
- Keep `.env.example` as a placeholder template.
- If the key is exposed, rotate it through the appropriate account controls.

## Step 8 — Check the Dream Labs SDK

Run:

```powershell
python scripts/check_dream_sdk.py
```

This checks the SDK import and the local API-key configuration. It is not a full simulator integration test.

If the check fails, record the exact error. Do not assume that a successful package installation proves the Playground workflow is configured correctly.

## Step 9 — Connect DreamGuard to Dream-1

Open:

```text
examples/dream_client_loop_skeleton.py
```

Review the example and compare it with the current official Dream Labs SDK and Playground example.

Confirm:

- How the Dream-1 client is initialized.
- How the policy is created.
- How observations and camera frames are supplied.
- The actual action schema.
- How actions are executed in the simulator.

The starter example includes the intended guarded-action workflow, but the simulator-specific observation and camera mappings must be completed using the official interface.

The key rule is:

```text
Dream-1 action
      |
      v
DreamGuard validation
      |
      +---- BLOCK ----> Stop; do not execute
      |
      +---- APPROVE --> Send to simulator
```

Do not connect the action directly to the execution method before it passes the required safety checks.

Connect your repository, replacing the placeholder with your actual GitHub username:


## 19. Final Product Positioning

**DreamGuard — The Safety Layer for AI-Driven Robotics**

Dream-1 gives robots the ability to understand instructions and generate actions. DreamGuard adds an independent validation layer that checks those actions before they are executed.

Instead of replacing the robot's AI policy, DreamGuard works alongside it.

The result is a more transparent and safety-conscious development workflow in which unsafe actions can be detected and blocked before they reach the simulator or controller.

**Hackathon pitch:**

> AI can decide what a robot should do. DreamGuard checks whether it should be allowed to do it.
